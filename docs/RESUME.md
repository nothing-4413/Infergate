## M0 —— 最小网关：OpenAI 兼容透传 + SSE 流式 + 基础计量

**一句话版（适合放简历项目标题下）**

> 从零实现 OpenAI 兼容推理网关，标准库零依赖完成反代透传与 SSE 逐帧转发，端到端断言 85 条全绿。

**项目符号版（建议 3–4 条）**

- 用 Go 标准库实现 OpenAI 兼容推理网关 M0：反向代理透传 `/v1/chat/completions` 等 5 类端点，
  请求体以 `map[string]json.RawMessage` 保字节重写（只改 model 字段，大整数/浮点不被格式化），
  响应错误体原样转发，保证 Agent 框架能依赖 provider 的 `error.type` 做重试决策。
- 自研 SSE 帧解析器与单 writer 中继：保留上游原始字节逐帧 `Flush`，实测注入 250ms 首帧停顿后
  客户端首帧到达 **268.0ms**（header 267.9ms），证明网关全程零缓冲；上游省略 `[DONE]` 时自动补齐，
  避免 OpenAI SDK 客户端挂死。
- 实现 `tool_call` 增量重组（按 `index` 累积 `arguments` 分片，实测 3 分片拼成合法 JSON）、
  usage/成本计量（采信 provider `usage`，含 `cached_tokens`，按单价折算 USD）、
  首字延迟打点（跳过 OpenAI 空 role 帧，在首个可见 token 处计时，避免 TTFT 虚低）。
- 建立可验证交付链路：Go 端到端验收程序 **38/38** 断言 + 真实进程 curl 验收脚本 **47/47** 断言
  （鉴权覆盖、路由命中、429/500/超时/404 故障注入、`[DONE]` 补齐、日志与 Prometheus 指标断言），
  `go vet` / `go test` 全绿，字节账目与日志 `resp_bytes` 逐字节对齐。

**可以现场讲的技术点（面试加分项）**

- 为什么出站 context 从 `context.Background()` 派生而不继承 `r.Context()`：`http.Server`
  在 handler 返回或读体失败时会取消入站 context，长流会被连带中断。
- 为什么 `max_idle_conns_per_host` 要从默认 2 提到 64：否则并发请求退化成"每请求新建 TCP+TLS"。
- 为什么模型不可解析返回 400 而不是 502：错误分类即责任划分，502 会污染上游健康度与后续熔断判定。
- 为什么 SSRF 防护要额外剔除 `Connection` 字段点名的头（RFC 7230 §6.1），而不是只删静态黑名单。

**待补实测数字 → 已回填（2026-10-05，本机实测）**

压测口径（写简历时务必带上，面试官一定会问"怎么测的"）：
`cmd/loadtest` 起真实 mock 上游子进程 + 真实网关进程，**本机回环**（同一台笔记本，
mock 注入延迟 0），每阶段 1500 请求 + 300 预热，**取 3 轮的 QPS 中位数**；机器同时跑着
编辑器等负载，因此**轮间抖动很大**（直连基线自身就有 40%+ 的轮间波动，见下表区间）。

- **流式首字延迟**：c=8 **P50 999us / P95 2.74ms**；c=32 **P50 2.00ms / P95 10.81ms**
  （mock 注入 ttfb=0）。另一组注入 250ms 停顿的验收里客户端首帧 **268.0ms**，说明网关零缓冲、几何级不吞首帧。
- **附加开销**：P95 上非流式 **+1.50ms**（c=8）/ **+2.99ms**（c=32），
  流式 **+4.09ms**（c=8）/ **+14.10ms**（c=32）；QPS 相对直连 **-25% ~ -40%**。
  这条数字要如实讲：它包含网关的双向拷贝 + JSON 解析/计量 + SSE 逐帧 Flush，本机单核竞争会放大它。
- **诚实的边界**：同一台机器上直连基线自身就有 40%+ 的轮间抖动，所以**只有毫秒级以上的差异才可信**；
  `/metrics` 里网关自己的处理耗时只有 1–5us/请求，远小于客户端观测的 1.6–24ms——
  说明这台机器上是**压测客户端（Go HTTP + SSE 解析 + JSON 解码）先成为瓶颈**，不是网关。
  简历上建议写"网关自身处理开销 ~us 级，端到端 P95 增加 X ms"，而不是把客户端等待算成网关的功绩。
- 原始数据：`docs/baseline/m0-baseline.json`；复现命令见 README 的"压测"一节。

## M1 —— 多 Provider 智能路由与故障转移

**一句话版（适合放简历项目标题下）**

> 为自研推理网关实现多 Provider 智能路由与故障转移：能力/健康/成本/延迟四因子选路 +
> 滑动窗口熔断 + 半开探测，杀掉 priority=1 副本期间 18000 请求 0 错误，
> 熔断把中位延迟从 420.42ms 压到 17.81ms（23.6×），双路端到端断言 205 条全绿。

**项目符号版（建议 3–4 条）**

- 设计并实现多 Provider 路由层（Go 标准库，无第三方路由库）：先按"模型是否匹配 + 能力标签是否满足"
  筛候选，再按 `priority / cost / latency / weighted / score` 五种策略排序；`score` 把成本、窗口实测延迟、
  可靠性（失败率）、优先级各自归一化到 0..1 后加权（权重是比例，不要求和为 1）。
  路由与打分不碰 IO、不改输入，所以策略可单测；"为什么选它"（如 `priority (priority 1)`、
  `priority: circuit open, only used as a last resort`）直接进结构化日志的 `reason=` 字段。
- 实现故障转移链路：连接错误 / 超时 / 5xx / 429 换后端重试，4xx 原样回传**并记为成功**
  （调用方自己的请求错不该污染上游健康度）；流式请求**只在首帧之前**可重试，已出帧绝不换后端，
  避免把两个后端的输出拼成一份自相矛盾的答案；`upstream_timeout` 按**每次尝试**独立计时，
  而不是整条请求共享——共享预算会让慢候选吃光时间、健康候选拿到已过期的 deadline，客户端 504
  而网关其实从未问过那个快后端。
- 实现按上游维度的滑动窗口熔断（时间分桶而非累计计数器：一小时前的失败不该压着现在）：
  窗口内 `min_requests` 以下不跳闸（未知 ≠ 坏了），失败率越阈值转 open，冷却后放半开探针，
  连续 N 个探针成功才回 closed；不健康的候选**排到最后而不是被剔除**，因此它仍是全熔断时的最后兜底。
  `max_failures_per_request` 是放大保护：三个坏后端各重试三次会把一个客户端请求变成九个上游请求。
- 建立可验证交付链路：Go 端到端验收 **64/64** 断言（累计 102 条）+ 真实进程 curl 验收 **56/56** 断言
  （累计 103 条），覆盖优先级/成本/延迟/加权/能力/显式指定六种选路、非流式与流式故障转移、
  熔断状态机与半开探针、全候选失败时回传最后一个 Provider 的错误体、四条可观测面
  （`/admin/upstreams`、`/admin/breakers`、`/stats`、`/metrics`）。

**可以现场讲的技术点（面试加分项）**

- 为什么 `upstream_timeout` 必须按"每次尝试"算：共享 deadline 下故障转移只是装饰——慢候选清零预算后，
  健康候选拿到过期 deadline，客户端拿 504 而快后端从未被问过。代价是最坏 `超时 × 尝试次数`，由配置权衡。
- 为什么流式只在首帧前重试：首帧之后重试会重复计费，并把两份 token 输出拼成一个"看起来正常"的答案。
- 为什么熔断把 open 的后端排最后而不是删掉：删掉就失去了"全挂了时还能试一次"的兜底语义；
  同时 4xx 必须记成功，否则调用方一个坏 payload 就能把健康上游熔断。
- 为什么能力用请求头而不是从 body 推断：同一模型在不同后端支持能力不同，且 Agent 框架无论是否真的
  调用工具都会带 tools schema——"看到 tools 字段就认为需要 tools"是明显而错误的猜测。

**实测数字（2026-10-05，本机实测，原始数据 `docs/baseline/m1-summary.json`）**

压测口径：单上游网关（M0 路径）与三副本路由网关（M1）**每轮交错**执行（本机基线自身有 40%+ 轮间抖动，
不交错就没有可比性），每阶段 1500 请求 + 300 预热，取 3 轮中位数；随后在同一进程中
`Stop-Process` 杀掉 priority=1 的副本，再压同样负载。

- **可用性**：中途杀掉 priority=1 副本后，该场景 **18000 请求 0 错误（100%）**，全部由 secondary 接管；
  整个实测 54000 请求同样 0 错误。注意这是本机 mock 的结论，验证的是"上游直接消失时网关的行为"，
  不等于真实 Provider 的 SLA。
- **熔断收益（逐请求量出来）**：1500ms 停顿后端 + 400ms 单次超时预算，共 10 个请求——前 4 个各付约
  418–423ms（第一次尝试超时后换到快后端，`tried='stalled, fast'`），第 5 个起熔断已 open
  （attempts=4 failures=4 timeouts=4 failure_ratio=1.0），**中位延迟 420.42ms → 17.81ms（23.6×）**，
  且只剩一次尝试、不再出现 `X-InferGate-Tried`。
- **路由开销**：M1 与 M0 同口径的 QPS/P95 差异全部落在轮间抖动以内（非流式 c=8：1749 vs 1772 QPS，
  P95 7.08ms vs 6.35ms），即候选筛选 + 打分 + 健康度查询的成本在本机量不出来。
- **故障发现的代价**：熔断窗口还没关掉死副本时，每个请求要先白跑一次死上游（非流式 c=8 掉到
  431 QPS、P50 19.5ms）；跳闸后同一轮后半段回到健康水平（非流式 c=32：1652 vs 健康 1701 QPS）。
  这是 `failure_ratio` / `min_requests` 的取舍，不是路由失效。

**与目标句式的差异（照实写，避免面试翻车）**

- 目标句式里的"路由表与打分权重**热加载**、不重启进程生效"**M1 没有实现**：配置在启动时加载并校验，
  改路由表要重启。热加载得先定义"部分生效"的语义（配置写坏了怎么回滚、旧连接池怎么回收），
  计划并入 M5 的运维完善。**简历里不要写热加载**，除非先补上。
- 目标句式里的"模型别名"在 M1 的形态是：后端声明 `["/", "自己的模型名"]` 时，请求会被改写成后端
  真实运行的模型名（`modelFor` 优先匹配具体名字，`"/"` 只表示"其它模型也能兜"）；
  更完整的别名表（外部名 → 多个后端各自的模型名）尚未实现。
- 目标句式里的 `【99.x%】` 占位替换为实测 **100%（18000/18000，故障场景，本机回环）**；
  "熔断后 P99 从 `【ms】` 降至 `【ms】`"替换为**中位延迟 420.42ms → 17.81ms（23.6×）**——
  这是用停顿后端逐请求量出来的，比用整轮压测的中位数更能说明熔断省下了什么。

## M2 —— 语义缓存（Embedding + 阈值门控）

**一句话版（适合放简历项目标题下）**

> 为自研推理网关实现语义缓存：Embedding + 余弦阈值门控 + 命中前身份校验（模型 / 温度 /
> max_tokens / 工具集 / response_format / 对话前缀指纹），命中路径 P95 **5.50ms**（未命中
> **47.31ms**）、每 1000 请求成本 **−56.39%**、上游进程被杀后仍 26/26 服务、26 对中英人工标注
> 语料**零误命中**，阈值 0.86 由扫描得出而非拍脑袋；双 store（进程内 LRU + Redis）跑同一套
> 一致性测试，流式命中按原帧逐帧回放，端到端断言 103 条全绿。

**项目符号版（建议 3–4 条）**

- 设计并实现语义缓存（Go 标准库 + 手写 RESP2 客户端，无第三方缓存/向量库依赖）：缓存插在
  **解析之后、路由之前**——命中时不需要知道有哪些后端，也不会污染熔断器的滑动窗口。
  一次判定由四个身份共同决定：`scope`（租户 + 模型 + 能力标签的哈希，多租户隔离）、
  `exact key`（客户端**原始**字节 + path + 租户；必须在模型名改写之前计算，否则同一模型的两个
  别名会得到两个键）、`signature`（答案形状：temperature / top_p / max_tokens / n / seed /
  stop / tools / tool_choice / response_format + **对话前缀全文指纹**）、以及最后一条
  user/tool 消息的文本。
- 把"命中"当成一个需要论证的结论而不是相似度的副产品：策略只做减法（`temperature > 0`、
  带 `tools`、提示过短一律退化为精确匹配，`bypass` / `refresh` 跳过查询但**仍然写入**），
  阈值由 `internal/evalset` 的 26 对人工标注语料（13 对同义改写 + 13 对近似但不同，中英各半）
  扫描得出：0.86 下误命中 **0/13**，而直觉值 0.94 只有 4/13 真命中、0.84 会把
  "删掉 tenant alpha 的缓存条目"命中"tenant beta"（错租户 = 数据事故）。
- 两个 Store 同一套一致性要求：memory 是进程内**真 LRU**（`container/list`），Redis 是跨副本共享、
  按创建时间 **FIFO** 淘汰（ZSET 报不出读取顺序，"对近期性撒谎的缓存比承认自己按年龄淘汰的更糟"，
  这条差异由测试显式钉住）；条目与向量分开存（检索只读紧凑的 base64 float32 hash），
  过期按条目记在 ZSET 里而非 key 级 `EXPIRE`（否则一个热问题会顺带延长同 scope 里陈旧答案的寿命）。
  启动时 ping 一次（配错要在启动时失败），运行中 store 死掉只降级为 miss 且 `/metrics` 仍 200。
- 建立可验证交付：Go 端到端验收 **103/103** 断言（进程内起真实 server，覆盖 miss→exact→semantic、
  语料中所有不该命中的对、租户/模型隔离、策略上限、流式逐帧重放、过期与 scope 上限、
  Redis 路径与 store 死亡降级、四个管理/观测面）+ 真实进程 curl 验收（内存与 Redis 两条路径）
  + 阈值扫描与命中率/延迟/成本实测脚本。

**可以现场讲的技术点（面试加分项）**

- 为什么缓存身份要包含**对话前缀**：Agent 循环里"同一句话"常常出现在不同的工具结果之后，
  只比最后一句话会把别的问题的答案发出去；前缀整体参与哈希，未知字段变了也会改变身份。
- 为什么 `temperature > 0` 仍然可以做**精确**命中、但永远不做语义命中：逐字节重试同一个采样
  请求就是同一件事，而换一种说法得到的样本是"给别人写的措辞"采出来的。
- 为什么命中**不写首 token 直方图**、也不算上游 token：把接近 0 的重放混进去，会让这个指标在
  缓存用得最狠的时候"变好"；同理命中时上游名记作 `cache`，否则按上游的账目会凭空多出从未到达的流量。
- 为什么阈值是配置项而不是常量：离线 `hashing` embedder 是**词法**的，语料里有 5 对真同义改写的
  相似度低于某个近似对——天花板是 embedder 的属性；换成真实 embedding 模型必须重跑扫描。
- 为什么语义缓存必须能被"只看缓存"地调试：`/admin/cache/lookup?prompt=` 给出最近邻与相似度，
  因为"没命中"和"命中了错的东西"在响应体里长得一模一样。

## M3 —— Token 配额与成本治理

**一句话版（适合放简历项目标题下）**

> 为网关实现多租户 Token 配额与成本治理：按租户 / 会话 / 日 / 分钟四个维度设限，准入插在
> **缓存查找之前**（命中免费，但仍占每分钟请求配额、仍进租户报表），账目用**预扣 + 结算**而不是
> "先用后记"（并发下先读后写必然超发），每个维度的预扣是**一条** `INCRBY` 原子操作、窗口进 key
> 而不是靠 TTL（TTL 过期的日桶会被迟到请求重建，静默重置当天预算）；超预算走梯度降级
> （换便宜模型 → 压 `max_tokens` → 拒绝并给 429 + `Retry-After`），估算与真实用量的差额显式记成
> `overshoot` / `released` 而不是藏起来，Redis 读不到时默认 **fail-closed**（读不到的预算不是预算）；
> 预算拦下 **97.5%** 本会打到上游的调用（40 个请求里 39 个被拒，上游调用 40 → 1），治理路径开销
> 落在本机轮间抖动内（并发 8：治理 2533 QPS / P95 5.42ms，不治理 2439 / 4.83ms）。

**项目符号版（建议 3–4 条）**

- 设计"准入 + 预扣 + 结算"的配额路径：日 token / 日成本 / 每分钟请求 / 每会话 token 四个维度
  各自独立设限，`Admit` 一次把所有维度都扣掉并把**第一个**越界维度作为拒绝原因返回；
  请求结束后按 provider 真实 `usage` 结算差额。三条顺序是承重的——准入在**缓存之前**
  （否则超预算的租户会继续从缓存拿答案，预算形同虚设）、只治理生成类路径
  （把 `/v1/models` 也计入会因为一个零成本请求拒绝调用方，并让 token 维度变成虚构）、
  降级请求**保留预扣**（降级后的请求仍然是一次请求、仍然要结算，便宜模型没用完的额度再还回去）。
- 把"原子扣减"落到真实可测的机制上：读代码发现 `internal/redis` 的 `Do` 每次从连接池取一条连接、
  调用之间不保留会话状态，所以 `MULTI`/`EXEC`/`WATCH` 会跨连接、**根本不是事务**，一个
  check-then-write 序列在那个客户端上就是竞态且看起来像正确。实现改成**单条命令原子**：
  每个维度的预扣是一条 `INCRBY`，读改写发生在 Redis 内部；窗口进 key
  （`ig:quota:<tenant>:day:<YYYYMMDD>:tokens`）而不是固定 key 上的 `EXPIRE`，因为"按 TTL 过期的
  日桶"会被一个迟到的请求重新创建；只有首次自增才发 `EXPIRE`。为此给自研 mockredis 补了
  `INCR/INCRBY/DECR/SETNX/SETEX/MGET/HINCRBY/ZINCRBY` 等命令，走真实 RESP2 派发（验收器因此在
  协议层被测过，而不是测一个 Go 方法）。
- 超预算不等于失败：`on_exceed: degrade` 且配了 `downgrade_model` 或 `max_tokens_cap` 时请求仍然
  放行，只是被改写——换模型（大小写不敏感，已经是目标模型就原样发）或把完成上限**压到** cap
  （只降不升：替调用方抬高上限等于网关替它花钱；body 用哪个拼写就改哪个，`max_completion_tokens`
  优先，两个同时出现会让不同 provider 作出不同解释）。两个杠杆都没配就在**配置校验期**报错，
  而不是在运行时"降级"成一个什么都没改的请求。估算必然不准，所以差额被显式记账：
  `actual − reserved > 0` 记 `overshoot_tokens` / `overshoot_cost_micros`（"这个软限额到底有多软"
  的唯一来源），`< 0` 记 `released_tokens`，而且**按维度分开记**：成本条目的返还进
  `released_cost_micros`。这条是实跑发现的——第一版把成本条目的返还也加进了 token 计数器，
  于是「释放了 1014 个 token」出现在一次只预扣 274 个 token 的请求上（1014 = 260 个真实 token
  + 754 微美元），读起来像预算异常；修好之后 `reserved − released + overshoot == settled`
  对每一笔预扣都成立。
- 建立可验证交付 + 真实的失败姿态：Redis 连不上时**启动失败**（`server: quota: redis at ...`）
  而不是退化成进程内存——那会让 N 个副本各自允许一整套日预算；运行期 store 抖动默认 fail-closed
  （503 + `infergate_quota_unavailable`），`fail_open: true` 给可用性优先的部署且响应头如实说明。
  异常检测（当日用量 vs 此前有流量几日均值）**只记日志和计数，从不拒绝请求**——花钱变多通常是
  真实业务，因为"看起来不寻常"拒绝流量的网关会把一次发布变成一次故障。验收：Go 端到端
  `cmd/verify-m3` **470** 条断言（内存与 Redis 两个 store、四个维度、降级与限长、结算/超支/释放、
  含 `:` 的租户名不得记到别人账上）+ 真实进程 curl 门禁 **323** 条断言 + `scripts/measure-m3.ps1`
  实测 **57** 条断言。

**可以现场讲的技术点（面试加分项）**

- 为什么不能用"先读后写"（GET 判断再 INCR）或"先用后记"（先转发再累加）：串行世界里两者都对，
  并发世界里 N 个请求都会看到"今天还剩 100 token"然后一起花掉——预扣是乐观记账，宁可先多扣后返还。
- 为什么窗口是 key 的一部分而不是 TTL：一个过期的日桶会被下一个请求重建，而重建的那一刻预算
  悄悄回到满额；窗口进 key 之后，"今天用了多少"就是一个普通 `GET`，跨天也不可能竞争。
- 为什么缓存命中按 `Usage{Requests: 1}` 结算、token 记 0：按条目里存的 token 收费，等于向租户收取
  provider 从未生成的 token，正好和缓存的用途相反；但请求数必须计，否则缓存会把每分钟限流变成摆设。
- 为什么拒绝要证明"上游没被调用"：拒绝如果发生在转发之后就是个 500 而不是配额；验收里用 mock
  自己记录的调用次数来证明，而不是相信网关的说法（同样的口径用在降级上：看后端实际收到的请求体）。
- 为什么 `overshoot` 是一个需要被看见的数字：它度量估算系统偏离现实的程度，持续增长意味着
  `estimate_chars_per_token` 对该租户的流量系统性偏低——这个结论只能从这两个计数器读出来。

**实测数字（本机实测，原始数据 `docs/baseline/m3-summary.json`）**

治理路径的开销（治理 vs 不治理两个网关，同一台机、同一次运行、3 轮交错，800 请求 + 100 预热 ×
并发 8/32，错误数全为 0）：

| 臂 | 并发 8 QPS / P95 | 并发 32 QPS / P95 |
| --- | --- | --- |
| 治理（配额全开，memory store） | 2533（轮间 2262–5231）/ 5.42ms | 2589（2517–5783）/ 14.49ms |
| 不治理（同一配置只关掉配额） | 2439（2136–3003）/ 4.83ms | 2632（2597–2697）/ 15.05ms |

- **治理开销落在这台机器的轮间抖动之内**：治理臂并发 8 的三轮是 5230 / 2262 / 2533 QPS（跨度
  2.3×），所以结论只能是"没有可测出的吞吐代价"，不能是"治理更快"。`/stats` 自视同一批请求：
  治理 p50 4.41 / P95 15.48ms，不治理 p50 4.74 / P95 15.49ms。
- 计数后端对比（都开治理）：memory 并发 8 QPS 2960 / P95 3.97ms、并发 32 3346 / 13.54ms；
  Redis（仓库内 miniredis，回环 RESP2）并发 8 2257 / 5.49ms、并发 32 2743 / 13.84ms——
  差额就是每个请求多出来的那几次 `INCRBY` / `GET` 往返。
- 预扣准不准（12 个真实请求，逐请求读 `/admin/quota` 增量对账）：预扣 **2872** token（= 逐请求
  估算公式之和，`len(body)/4 + 256`）、真实结算 **320**（= 各响应 `usage` 之和 = 租户日计数器）、
  返还 **2608**、超支 **56** token / **171** 微美元，`reserved − released + overshoot == settled`
  成立；**平均绝对偏差 222 token，平均有符号偏差 +212.7**（系统性高估：完成侧按 256 预扣，
  而 mock 的回答只有 4 个词）。
- 预算到底挡下了什么（40 个请求的工作量）：不设预算时 40/40 全部打到上游（40×200，4.99s）；
  把该租户日预算压到 280 token 后变成 **1×200 + 39×429（97.5% 被拒）**，上游调用 **40 → 1**，
  租户 `tokens_today` 停在 9——用 mock 自己记录的调用次数证明，而不是相信网关的说法。
- 故障姿态（真进程，杀 miniredis）：fail-closed 下 20/20 请求得到 503 `store-error`、上游调用
  **0**、`store_errors` 20；重启 store 后同一个网关进程（PID 未变）10/10 恢复 200。
  只把 `fail_open` 翻成 true 的同一次故障里 5/5 放行、5 次上游调用。
- 降级梯子（租户 `growth`）：预算内 → 200 `allow` + `mock-gpt`；日预算压到 20 且
  `max_tokens_cap: 64` → 200 `degrade` + `mock-gpt-mini` + 上限头 64，后端日志确认收到的模型名
  就是 `mock-gpt-mini`。
- Escape hatch 的证据：裸 RESP2 `GET ig:quota:key-70762936d0600d56:day:20261005:tokens`
  连续三轮读回 32238 → 64305 → 96327，分钟键 `…:minute:202610051038:requests` 7200。
- 口径说明（会被追问的部分）：上游是仓库内 mock（本地免费，没有 provider 账单），所以上面的
  QPS/P95 差额是**网关自身多做的工作**（扫 body + 估算 + store 往返），不是 provider 延迟的节省；
  mock 的 token 口径是"空格分词"（prompt = 词数 + 4），所以 +212.7 的系统性高估是这个配对的属性，
  不是估算公式的普适结论；降级把 `max_tokens` 改写进了转发体，但 `cmd/mockupstream` 完全忽略
  `max_tokens`，所以"降级省了多少 token"这一项**测不出来**（只证明了改写发生）；Redis 臂是仓库内
  协议实现，验的是代码路径与键布局，不是生产 Redis；fail-open 的决策计数天然不完整（store 没记上
  那几笔），可信度低于 fail-closed 臂；日预算是 **UTC 天**，UTC+8 的机器上本地 08:00 重置。
  复现命令 `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\measure-m3.ps1`。

## M4 —— vLLM 本地推理服务化与量化对比

**一句话版（适合放简历项目标题下）**

> 给网关加了分层路由（`tier: local | cloud` + `routing.tier_policy`）并把它接到一块 8GB 笔记本显卡上
> 真实的 vLLM：用"序列化消息长度 / 4"（与 M3 预扣估算同一个常数）判断请求是简单还是难，短请求本地
> 优先、长请求云端优先——分层是**排序而不是过滤**，所以跨层故障转移与 M1 的能力筛选都还在；本地层
> 是 WSL2 里真的 vLLM（Qwen2.5-1.5B，FP16 / AWQ / GPTQ 三档都跑过），量化把吞吐从 41.5 提到
> **100.7 tok/s（2.42×）**、端到端 P50 从 1758ms 降到 **700ms（−60%）**，但 12 条固定 prompt 里
> **0 条**与 FP16 逐字一致（token 重合 0.44，其中一道算术题 AWQ 把差值答成了负数）——所以结论是
> "量化让这张卡可用"，而不是"量化不掉质量"；分层分流实测 16 个请求里 **8/8 短请求落本地、8/8 长请求
> 落云端**，按云侧挂牌价折算掉 **34.52%** 的云侧账单。

**项目符号版（建议 3–4 条）**

- 把"本地 / 云端"做成上游的一个 `tier` 字段加一条 `routing.tier_policy`，并明确分层是**排序**：
  健康优先（熔断打开的本地层输给健康的云端层）、其次偏好层、再次优先级、最后配置顺序；难请求仍然
  把本地留在后面，所以本地挂了会自然退回云端；能力筛选（`tools` / `vision`）照旧先过滤——把工具调用
  发到不会调工具的本地模型，得到的是一段合规的散文，比 502 更难发现。决策面只有既有的 reason 字符串
  （`strategy=tiered tier=local reason=simple request prefers this tier`），没有新增指标标签。
- 分类口径选**长度**不选模型名，理由写进了设计文档：本地上游配的是 catch-all（`models: ["/"]`），
  它能答任何模型名，所以模型名不携带难度信息，按模型名分层等于把"这条难不难"交给调用方；长度估算
  零 I/O、且和 M3 的配额预扣共用 `config.EstimateCharsPerToken`，于是"长 prompt"对路由和配额是同一个
  意思（边界是确定性的：1600 字节 = 估算 400 token，正好压在阈值上）。
- 真机推理的三次依赖事故（都写进 DESIGN §11.4）：vLLM 0.31 只有 CUDA 13 轮子而本机驱动 560.94 只到
  12.6，torch 直接看不到卡（钉到 `vllm==0.11.0` + torch 2.8.0+cu128）；vLLM 对 transformers 只有下界，
  而 5.x 删掉了 `all_special_tokens_extended`（钉 `>=4.55.2,<5`）；`torch.compile` 默认开、Inductor 需要
  gcc（补 `build-essential`）。环境上还有一层：本机 pypi.org 与 huggingface.co 都不可达（pip 走清华镜像，
  模型走 hf-mirror），而 hf-mirror 传 1.6GB 的 AWQ 权重到 732MB 直接停住不动，同一个文件从 ModelScope
  取快 6–12×（1.61GB / 2.3 分钟，字节数与 `Content-Length` 对齐）。
- 顺带修掉一处"只写在文档里"的死配置：`routing.fallback_model` 现在真的生效——只在**选中的上游不服务
  所请求模型、且这个上游确实服务 fallback 模型**时才改写（catch-all 永不触发改写），定价与日志都跟随
  改写后的模型，否则"回退"会让账单记在错的模型上。

**可以现场讲的技术点（面试加分项）**

- 为什么"层间延迟差"在这份数据里不能读成"本地比云端慢"：云端层是仓库内 mock（秒回），本地层是真模型
  在笔记本 GPU 上逐字生成；而且本地臂在同一台机上两分钟内从 784.5ms 变到 560.4ms（−29%），所以只能
  引用同一次运行内部的两层对比，跨运行的绝对值没有意义。
- 为什么"显存增量"不能当模型体积：vLLM 按 `--gpu-memory-utilization 0.85` 预分配 KV cache，权重越小
  留给缓存的越多，于是 1.61GB 的 AWQ 增量（+6921 MiB）反而比 3.09GB 的 FP16（+6169 MiB）更大；
  `nvidia-smi` 报的 used 还包含 Windows 桌面的 1.7–1.9GiB，所以只读差值、±50 MiB 以内不算差异。
- 为什么量化对比要报"漂移"而不是"准确率"：12 条固定 prompt 上 AWQ 0/12、GPTQ 1/12 与 FP16 逐字一致，
  但 token 重合 0.44–0.46，且错的方式是具体的（`4873+6259` 的差 FP16/GPTQ 答 1386、AWQ 答 −1386；
  "澳大利亚人口（百万）" FP16 说 4.1、AWQ 说 40、GPTQ 说 2.8）——这说明输出没有崩坏，但数字和措辞
  都会漂移，没有标尺就不能把"重合度"说成"质量保留率"。
- 为什么"省下的钱"要写成"账面替代"：本地层现金边际成本是 0，但 `pricing` 按模型名定价、两层都答
  `local-chat`，所以网关给本地请求记的仍是云侧单价——这个数诚实的名字是"被替代掉的云侧挂牌价"，
  不是"少付的账单"（本地免费这件事本身写在配置的注释里，而不是伪装成账单）。
- 为什么分流比例要用网关自己的 per-upstream `/stats` 计数证明：脚本自己记的"我发了 8 条"不能证明
  请求真的落到了本地层，`/stats` 的 local +8 / cloud +8 加上"每个本地答案非空且带 `usage`"才证明走的是
  真模型的生成路径。

**实测数字（本机实测，原始数据 `docs/baseline/m4-summary.json`）**

量化对比（三档同一套 12 条固定 prompt，逐条非流式、单并发、greedy、`max_tokens 128`、预热 2 条，
同一张 RTX 4070 Laptop 8GB / i9 / 32GB，vLLM 0.11.0 + torch 2.8.0+cu128）：

| 变体 | 权重大小 | 加载 | TTFT P50 | 端到端 P50 | 吞吐 | 显存增量 | 与 FP16 逐字一致 | token 重合 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| FP16 | 3.09 GB | 58s | 35.2ms | 1758.5ms | 41.5 tok/s | +6169 MiB | — | — |
| AWQ | 1.61 GB | 60s | 28.1ms | 699.5ms | **100.7 tok/s** | +6921 MiB | 0/12 | 0.444 |
| GPTQ-Int4 | 1.15 GB | 55s | 28.7ms | 723.6ms | 95.3 tok/s | +7353 MiB | 1/12 | 0.460 |

分层分流（本地层 = 真 vLLM 的 AWQ 权重，云端层 = 仓库内 `mockupstream`，一层 8 条短请求、一层 8 条
2444 字符的长请求，共 16 条、单并发）：

| 层 | 接到 | 客户端 P50 / P95 | token（prompt / completion） | 按挂牌价折算 |
| --- | --- | --- | --- | --- |
| 本地 `local-vllm` | 8/8 短请求 | 560.4 / 946.2ms | 312 / 421 | 0.00054734 USD |
| 云端 `cloud-mock` | 8/8 长请求 | 71.8 / 135.2ms | 3096 / 184 | 0.00103832 USD |

- 分流的判据是可复现的：8/8 与 8/8 在两个方向上都成立，网关 `/stats` 的 per-upstream 增量同为
  local +8 / cloud +8（对整批 16 条，网关自己的 `/stats` 是 P50 342.6 / P95 851.8ms），且本地层的
  答案全部非空并带 `usage`。
- **省下的云侧花费 = 0.00054734 USD = 34.52%**：全批 16 条若都走云侧是 0.00158566 USD，被本地接住的
  8 条按云侧单价折算为 0.00054734，云端层自身仍是 0.00103832（`avoided + cloud_served == all_cloud`
  有断言钉住）。这个数在三次运行里逐字节复现（8/8、50%、同样的 token 和同样的 34.52%）。
- 三次运行里**只有本地臂的延迟不复现**：P50 627.2 → 784.5 → 560.4ms，3.5 分钟内摆幅约 40%——所以
  分流与花费可以跨运行引用，延迟只能同一次运行内部比。
- 口径说明（会被追问的部分）：云端层是仓库内 mock，所以跨层延迟差不是"本地 vs 真云"的比较，也没有
  真的产生账单，成本是**按挂牌价折算**而不是计费；一致率是"文本漂移"不是准确率（12 条 prompt、单并发、
  一轮，给的是差异不是分布）；显存增量含 KV cache 预分配与 Windows 桌面占用；分流只覆盖两种固定形态
  （16 条、单并发、非流式），证明的是这个 mix 下的分类与分流，不是负载下的行为。
- 验收：Go 端到端 `cmd/verify-m4` **877** 条断言 + 真实进程 curl 门禁 `scripts\verify-m4.ps1` **125** 条
  断言（两个假 tier，不需要 GPU）+ `scripts/measure-m4.ps1` 实测 **63** 条断言。
  复现命令 `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\measure-m4.ps1 -SkipBench`。
