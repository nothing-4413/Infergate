## M0 —— 最小网关：OpenAI 兼容透传 + SSE 流式 + 基础计量

**一句话版（适合放简历项目标题下）**

> 从零实现 OpenAI 兼容推理网关，标准库零依赖完成反代透传与 SSE 逐帧转发，端到端断言 85 条全绿。

**项目符号版（建议 3–4 条）**

- 用 Go 标准库实现 OpenAI 兼容推理网关 M0：反向代理透传 `/v1/chat/completions` 等 5 类端点，
  请求体以 `map[string]json.RawMessage` 保字节重写（只改 model 字段，大整数/浮点不被格式化），
  响应错误体原样转发，保证 Agent 框架能依赖 provider 的 `error.type` 做重试决策。
- 自研 SSE 帧解析器与单 writer 中继：保留上游原始字节逐帧 `Flush`，实测注入 250ms 首帧停顿后
  客户端首帧到达 **268.0ms**（header 267.9ms），证明网关全程零缓冲；上游省略 `[DONE]` 时自动补齐，
  避免 OpenAI SDK 客户端挂死。
- 实现 `tool_call` 增量重组（按 `index` 累积 `arguments` 分片，实测 3 分片拼成合法 JSON）、
  usage/成本计量（采信 provider `usage`，含 `cached_tokens`，按单价折算 USD）、
  首字延迟打点（跳过 OpenAI 空 role 帧，在首个可见 token 处计时，避免 TTFT 虚低）。
- 建立可验证交付链路：Go 端到端验收程序 **38/38** 断言 + 真实进程 curl 验收脚本 **47/47** 断言
  （鉴权覆盖、路由命中、429/500/超时/404 故障注入、`[DONE]` 补齐、日志与 Prometheus 指标断言），
  `go vet` / `go test` 全绿，字节账目与日志 `resp_bytes` 逐字节对齐。

**可以现场讲的技术点（面试加分项）**

- 为什么出站 context 从 `context.Background()` 派生而不继承 `r.Context()`：`http.Server`
  在 handler 返回或读体失败时会取消入站 context，长流会被连带中断。
- 为什么 `max_idle_conns_per_host` 要从默认 2 提到 64：否则并发请求退化成"每请求新建 TCP+TLS"。
- 为什么模型不可解析返回 400 而不是 502：错误分类即责任划分，502 会污染上游健康度与后续熔断判定。
- 为什么 SSRF 防护要额外剔除 `Connection` 字段点名的头（RFC 7230 §6.1），而不是只删静态黑名单。

**待补实测数字 → 已回填（2026-10-05，本机实测）**

压测口径（写简历时务必带上，面试官一定会问"怎么测的"）：
`cmd/loadtest` 起真实 mock 上游子进程 + 真实网关进程，**本机回环**（同一台笔记本，
mock 注入延迟 0），每阶段 1500 请求 + 300 预热，**取 3 轮的 QPS 中位数**；机器同时跑着
编辑器等负载，因此**轮间抖动很大**（直连基线自身就有 40%+ 的轮间波动，见下表区间）。

- **流式首字延迟**：c=8 **P50 999us / P95 2.74ms**；c=32 **P50 2.00ms / P95 10.81ms**
  （mock 注入 ttfb=0）。另一组注入 250ms 停顿的验收里客户端首帧 **268.0ms**，说明网关零缓冲、几何级不吞首帧。
- **附加开销**：P95 上非流式 **+1.50ms**（c=8）/ **+2.99ms**（c=32），
  流式 **+4.09ms**（c=8）/ **+14.10ms**（c=32）；QPS 相对直连 **-25% ~ -40%**。
  这条数字要如实讲：它包含网关的双向拷贝 + JSON 解析/计量 + SSE 逐帧 Flush，本机单核竞争会放大它。
- **诚实的边界**：同一台机器上直连基线自身就有 40%+ 的轮间抖动，所以**只有毫秒级以上的差异才可信**；
  `/metrics` 里网关自己的处理耗时只有 1–5us/请求，远小于客户端观测的 1.6–24ms——
  说明这台机器上是**压测客户端（Go HTTP + SSE 解析 + JSON 解码）先成为瓶颈**，不是网关。
  简历上建议写"网关自身处理开销 ~us 级，端到端 P95 增加 X ms"，而不是把客户端等待算成网关的功绩。
- 原始数据：`docs/baseline/m0-baseline.json`；复现命令见 README 的"压测"一节。

## M1 —— 多 Provider 智能路由与故障转移

**一句话版（适合放简历项目标题下）**

> 为自研推理网关实现多 Provider 智能路由与故障转移：能力/健康/成本/延迟四因子选路 +
> 滑动窗口熔断 + 半开探测，杀掉 priority=1 副本期间 18000 请求 0 错误，
> 熔断把中位延迟从 420.42ms 压到 17.81ms（23.6×），双路端到端断言 205 条全绿。

**项目符号版（建议 3–4 条）**

- 设计并实现多 Provider 路由层（Go 标准库，无第三方路由库）：先按"模型是否匹配 + 能力标签是否满足"
  筛候选，再按 `priority / cost / latency / weighted / score` 五种策略排序；`score` 把成本、窗口实测延迟、
  可靠性（失败率）、优先级各自归一化到 0..1 后加权（权重是比例，不要求和为 1）。
  路由与打分不碰 IO、不改输入，所以策略可单测；"为什么选它"（如 `priority (priority 1)`、
  `priority: circuit open, only used as a last resort`）直接进结构化日志的 `reason=` 字段。
- 实现故障转移链路：连接错误 / 超时 / 5xx / 429 换后端重试，4xx 原样回传**并记为成功**
  （调用方自己的请求错不该污染上游健康度）；流式请求**只在首帧之前**可重试，已出帧绝不换后端，
  避免把两个后端的输出拼成一份自相矛盾的答案；`upstream_timeout` 按**每次尝试**独立计时，
  而不是整条请求共享——共享预算会让慢候选吃光时间、健康候选拿到已过期的 deadline，客户端 504
  而网关其实从未问过那个快后端。
- 实现按上游维度的滑动窗口熔断（时间分桶而非累计计数器：一小时前的失败不该压着现在）：
  窗口内 `min_requests` 以下不跳闸（未知 ≠ 坏了），失败率越阈值转 open，冷却后放半开探针，
  连续 N 个探针成功才回 closed；不健康的候选**排到最后而不是被剔除**，因此它仍是全熔断时的最后兜底。
  `max_failures_per_request` 是放大保护：三个坏后端各重试三次会把一个客户端请求变成九个上游请求。
- 建立可验证交付链路：Go 端到端验收 **64/64** 断言（累计 102 条）+ 真实进程 curl 验收 **56/56** 断言
  （累计 103 条），覆盖优先级/成本/延迟/加权/能力/显式指定六种选路、非流式与流式故障转移、
  熔断状态机与半开探针、全候选失败时回传最后一个 Provider 的错误体、四条可观测面
  （`/admin/upstreams`、`/admin/breakers`、`/stats`、`/metrics`）。

**可以现场讲的技术点（面试加分项）**

- 为什么 `upstream_timeout` 必须按"每次尝试"算：共享 deadline 下故障转移只是装饰——慢候选清零预算后，
  健康候选拿到过期 deadline，客户端拿 504 而快后端从未被问过。代价是最坏 `超时 × 尝试次数`，由配置权衡。
- 为什么流式只在首帧前重试：首帧之后重试会重复计费，并把两份 token 输出拼成一个"看起来正常"的答案。
- 为什么熔断把 open 的后端排最后而不是删掉：删掉就失去了"全挂了时还能试一次"的兜底语义；
  同时 4xx 必须记成功，否则调用方一个坏 payload 就能把健康上游熔断。
- 为什么能力用请求头而不是从 body 推断：同一模型在不同后端支持能力不同，且 Agent 框架无论是否真的
  调用工具都会带 tools schema——"看到 tools 字段就认为需要 tools"是明显而错误的猜测。

**实测数字（2026-10-05，本机实测，原始数据 `docs/baseline/m1-summary.json`）**

压测口径：单上游网关（M0 路径）与三副本路由网关（M1）**每轮交错**执行（本机基线自身有 40%+ 轮间抖动，
不交错就没有可比性），每阶段 1500 请求 + 300 预热，取 3 轮中位数；随后在同一进程中
`Stop-Process` 杀掉 priority=1 的副本，再压同样负载。

- **可用性**：中途杀掉 priority=1 副本后，该场景 **18000 请求 0 错误（100%）**，全部由 secondary 接管；
  整个实测 54000 请求同样 0 错误。注意这是本机 mock 的结论，验证的是"上游直接消失时网关的行为"，
  不等于真实 Provider 的 SLA。
- **熔断收益（逐请求量出来）**：1500ms 停顿后端 + 400ms 单次超时预算，共 10 个请求——前 4 个各付约
  418–423ms（第一次尝试超时后换到快后端，`tried='stalled, fast'`），第 5 个起熔断已 open
  （attempts=4 failures=4 timeouts=4 failure_ratio=1.0），**中位延迟 420.42ms → 17.81ms（23.6×）**，
  且只剩一次尝试、不再出现 `X-InferGate-Tried`。
- **路由开销**：M1 与 M0 同口径的 QPS/P95 差异全部落在轮间抖动以内（非流式 c=8：1749 vs 1772 QPS，
  P95 7.08ms vs 6.35ms），即候选筛选 + 打分 + 健康度查询的成本在本机量不出来。
- **故障发现的代价**：熔断窗口还没关掉死副本时，每个请求要先白跑一次死上游（非流式 c=8 掉到
  431 QPS、P50 19.5ms）；跳闸后同一轮后半段回到健康水平（非流式 c=32：1652 vs 健康 1701 QPS）。
  这是 `failure_ratio` / `min_requests` 的取舍，不是路由失效。

**与目标句式的差异（照实写，避免面试翻车）**

- 目标句式里的"路由表与打分权重**热加载**、不重启进程生效"**M1 没有实现**：配置在启动时加载并校验，
  改路由表要重启。热加载得先定义"部分生效"的语义（配置写坏了怎么回滚、旧连接池怎么回收），
  计划并入 M5 的运维完善。**简历里不要写热加载**，除非先补上。
- 目标句式里的"模型别名"在 M1 的形态是：后端声明 `["/", "自己的模型名"]` 时，请求会被改写成后端
  真实运行的模型名（`modelFor` 优先匹配具体名字，`"/"` 只表示"其它模型也能兜"）；
  更完整的别名表（外部名 → 多个后端各自的模型名）尚未实现。
- 目标句式里的 `【99.x%】` 占位替换为实测 **100%（18000/18000，故障场景，本机回环）**；
  "熔断后 P99 从 `【ms】` 降至 `【ms】`"替换为**中位延迟 420.42ms → 17.81ms（23.6×）**——
  这是用停顿后端逐请求量出来的，比用整轮压测的中位数更能说明熔断省下了什么。

## M2 —— 语义缓存（Embedding + 阈值门控）

**一句话版（适合放简历项目标题下）**

> 为自研推理网关实现语义缓存：Embedding + 余弦阈值门控 + 命中前身份校验（模型 / 温度 /
> max_tokens / 工具集 / response_format / 对话前缀指纹），命中路径 P95 **5.50ms**（未命中
> **47.31ms**）、每 1000 请求成本 **−56.39%**、上游进程被杀后仍 26/26 服务、26 对中英人工标注
> 语料**零误命中**，阈值 0.86 由扫描得出而非拍脑袋；双 store（进程内 LRU + Redis）跑同一套
> 一致性测试，流式命中按原帧逐帧回放，端到端断言 103 条全绿。

**项目符号版（建议 3–4 条）**

- 设计并实现语义缓存（Go 标准库 + 手写 RESP2 客户端，无第三方缓存/向量库依赖）：缓存插在
  **解析之后、路由之前**——命中时不需要知道有哪些后端，也不会污染熔断器的滑动窗口。
  一次判定由四个身份共同决定：`scope`（租户 + 模型 + 能力标签的哈希，多租户隔离）、
  `exact key`（客户端**原始**字节 + path + 租户；必须在模型名改写之前计算，否则同一模型的两个
  别名会得到两个键）、`signature`（答案形状：temperature / top_p / max_tokens / n / seed /
  stop / tools / tool_choice / response_format + **对话前缀全文指纹**）、以及最后一条
  user/tool 消息的文本。
- 把"命中"当成一个需要论证的结论而不是相似度的副产品：策略只做减法（`temperature > 0`、
  带 `tools`、提示过短一律退化为精确匹配，`bypass` / `refresh` 跳过查询但**仍然写入**），
  阈值由 `internal/evalset` 的 26 对人工标注语料（13 对同义改写 + 13 对近似但不同，中英各半）
  扫描得出：0.86 下误命中 **0/13**，而直觉值 0.94 只有 4/13 真命中、0.84 会把
  "删掉 tenant alpha 的缓存条目"命中"tenant beta"（错租户 = 数据事故）。
- 两个 Store 同一套一致性要求：memory 是进程内**真 LRU**（`container/list`），Redis 是跨副本共享、
  按创建时间 **FIFO** 淘汰（ZSET 报不出读取顺序，"对近期性撒谎的缓存比承认自己按年龄淘汰的更糟"，
  这条差异由测试显式钉住）；条目与向量分开存（检索只读紧凑的 base64 float32 hash），
  过期按条目记在 ZSET 里而非 key 级 `EXPIRE`（否则一个热问题会顺带延长同 scope 里陈旧答案的寿命）。
  启动时 ping 一次（配错要在启动时失败），运行中 store 死掉只降级为 miss 且 `/metrics` 仍 200。
- 建立可验证交付：Go 端到端验收 **103/103** 断言（进程内起真实 server，覆盖 miss→exact→semantic、
  语料中所有不该命中的对、租户/模型隔离、策略上限、流式逐帧重放、过期与 scope 上限、
  Redis 路径与 store 死亡降级、四个管理/观测面）+ 真实进程 curl 验收（内存与 Redis 两条路径）
  + 阈值扫描与命中率/延迟/成本实测脚本。

**可以现场讲的技术点（面试加分项）**

- 为什么缓存身份要包含**对话前缀**：Agent 循环里"同一句话"常常出现在不同的工具结果之后，
  只比最后一句话会把别的问题的答案发出去；前缀整体参与哈希，未知字段变了也会改变身份。
- 为什么 `temperature > 0` 仍然可以做**精确**命中、但永远不做语义命中：逐字节重试同一个采样
  请求就是同一件事，而换一种说法得到的样本是"给别人写的措辞"采出来的。
- 为什么命中**不写首 token 直方图**、也不算上游 token：把接近 0 的重放混进去，会让这个指标在
  缓存用得最狠的时候"变好"；同理命中时上游名记作 `cache`，否则按上游的账目会凭空多出从未到达的流量。
- 为什么阈值是配置项而不是常量：离线 `hashing` embedder 是**词法**的，语料里有 5 对真同义改写的
  相似度低于某个近似对——天花板是 embedder 的属性；换成真实 embedding 模型必须重跑扫描。
- 为什么语义缓存必须能被"只看缓存"地调试：`/admin/cache/lookup?prompt=` 给出最近邻与相似度，
  因为"没命中"和"命中了错的东西"在响应体里长得一模一样。
